# Phase 17 — Dataset selection

## Selected corpus

**NVIDIA OpenCodeReasoning-2, Python split**, pinned to repository revision `eadf535931451525f3e5621d0f960c240bc62fd9` (metadata query date 2026-09-27). Source: [Hugging Face dataset card](https://huggingface.co/datasets/nvidia/OpenCodeReasoning-2).

The dataset card reports approximately 1.4 million Python examples across 34,125 distinct questions. It includes a generated solution, a QwQ-generated critique and judgement (`right`/`wrong`), `pass_rate` (0–1, or -1 when unavailable), question ID, source, difficulty, and upstream license fields. The question text field is blank in this release; its card describes a join to upstream question datasets. This experiment will not perform that join. Therefore its model uses code plus non-label metadata only, never critique/judgement or pass_rate as input features.

## Target and scope

The target is the source-recorded `pass_rate`, modeled as regression on Python solution code and a restricted set of metadata fields. Rows with missing/invalid pass_rate or no code are excluded. This estimates a dataset-specific execution test pass rate for competitive-programming solution submissions. It does not determine factual truth, does not predict CodeGuard's Supported/Contradicted/Insufficient Evidence labels, and does not replace execution in an isolated environment, deterministic static checks, or evidence retrieval.

The source card says the responses were generated by R1 and critiques by QwQ; its labeling method is hybrid/automated/synthetic. Although `pass_rate` is described as a test outcome, it may be unavailable for items without enough unit tests or where the execution system could not validate. It is not independent human review. We exclude generated critique and judgement entirely to avoid target leakage and avoid representing them as human labels.

## Why this selection

Among the surveyed options, this one combines a large Python subset with a numeric execution-related signal. HumanEval and MBPP are much too small for training. TACO has tests and topic/difficulty fields but fewer than 27K problems and mixed source terms. CodeSearchNet is valuable for retrieval, but source licenses are per-repository and its main corpus lacks correctness outcomes. The earlier OpenCodeReasoning release has difficulty metadata but lacks pass-rate/judgement. OpenCodeReasoning-2 is the closest scale/task fit without inventing a CodeGuard mapping.

## License and attribution controls

The Hugging Face dataset card states that the collection is CC BY 4.0 and warns that the original upstream datasets are subject to their own terms. The row-level `license` field must be retained. The preprocessing pipeline accepts only explicitly recognized permissive records (`apache-2.0`, `mit`, `cc-by-4.0`) and reports every other value as excluded. This is a technical filter, not legal advice or a substitute for upstream terms review. The resulting artifacts and reports retain NVIDIA attribution, dataset/revision URLs, and row source/licensing fields.

## Dataset split and leakage controls

The source split is `train`; no official held-out split is claimed for this downstream experiment. The experiment creates fixed-seed 70/15/15 train/validation/test partitions grouped by `question_id`, removes exact duplicate rows before partitioning, and audits normalized code hashes across partitions. If question reconstruction/source joins become available in a future phase, source problem IDs and upstream split boundaries should also be preserved. The source provides 34,125 distinct questions for 1,398,166 Python records, so groups, rather than rows, are the split unit.

## Download scope

For the bounded run, download the first three contiguous Parquet shards from the pinned Python split. The original dataset card reports 1,398,166 Python rows over 70 shards, so these shards are a reproducible prefix sample, not the complete corpus. The exact downloaded, licensed, valid and split counts are generated in the Phase 17 reports after parsing. The preferred 50K usable target will be checked after all filters; if filtering falls below it, the experiment will report the smaller count without relaxing quality criteria.
